# Running on the iOS Simulator

Like Android, this app has native modules (`react-native-purchases`, Firebase Auth, Google Sign-In,
notifications) so it **cannot run in plain Expo Go**. On iOS, since Xcode is installed locally, the
simplest path is a local dev-client build — no EAS/Apple Developer account needed for the simulator.

## Prerequisites (one-time)

- Xcode installed, with command line tools selected: `xcode-select -p`
- CocoaPods installed: `pod --version` (install via `brew install cocoapods` if missing)

## First build (or after adding/updating a native module)

```bash
open -a Simulator   # optional, npm run ios will boot one if needed
npm run ios          # = expo run:ios: prebuild -> pod install -> xcodebuild -> install + launch
```

This regenerates the `ios/` folder (gitignored, same as `android/`) from `app.json`, so it always
picks up config changes. First run takes several minutes.

## Day-to-day (no native changes)

```bash
npx expo start --dev-client
```

Press `i` to launch/reload on the simulator. Only re-run `npm run ios` when a native dependency or
its config plugin changes — this path just reloads JS via Metro against the already-built app.

## Why `expo-build-properties` is in `app.json`

The first local build failed `pod install` with:

```
The Swift pod FirebaseAuth depends upon FirebaseAuthInterop, FirebaseAppCheckInterop, GoogleUtilities,
and RecaptchaInterop, which do not define modules... you may set use_modular_headers!
```

This happens because CocoaPods builds pods as plain static libraries by default, and these Swift pods
(pulled in by `@react-native-firebase/auth`) need module maps to be importable from Swift.

The fix is **not** to hand-edit `ios/Podfile` — it's regenerated by `expo prebuild` every time, so any
edit there is silently lost. Instead, the `expo-build-properties` config plugin in `app.json` sets:

```json
["expo-build-properties", { "ios": { "useFrameworks": "static" } }]
```

This makes CocoaPods build every pod as a proper framework (`use_frameworks! :linkage => :static`),
which generates the module maps Firebase needs.

Note: `useFrameworks: "dynamic"` also fixes the Firebase error (any framework mode generates module
maps), but it broke linking for `RNPurchases` instead — `ld: symbol(s) not found for architecture arm64`
for `RCTEventEmitter`/`RCTRegisterModule`, because React Native's prebuilt `React-Core-prebuilt`
binary doesn't export those symbols correctly to a dynamically-linked framework. `static` is the
setting that satisfies both.

## Known simulator limitations

- Notification **permission prompts** work fine.
- **Actual push delivery** (remote APNs) does not work in the simulator — local notifications and the
  permission dialog do; end-to-end push testing needs a real device.
- RevenueCat/`react-native-purchases`: the simulator can't hit real StoreKit/App Store sandbox — use a
  StoreKit configuration file, or a physical device with a sandbox tester account, to test purchases.
